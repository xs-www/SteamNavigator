# Steam Navigator 模组实体与约束规范

-   **文档类型**：设计规范 / Schema 约束
-   **适用范围**：SNModMaker、模组内容、注册表、发布校验与运行时装配
-   **版本**：Draft 0.1
-   **状态**：待对照现有代码确认
-   **设计目标**：统一实体约束、合并重复的船舶模块实体类型、建立跨实体引用与组合校验规则。

> 本文定义目标架构，不代表当前仓库已经实现这些字段或规则。正式实施前，应核对现有实体定义、Schema
> 加载器、注册表和运行时读取代码。本文中的 JSON
> 主要是实体数据示例与约束声明示意，不是完整 JSON Schema Draft 2020-12。

------------------------------------------------------------------------

## 1. 设计原则

1.  **统一实体契约**：所有内容实体遵守统一的
    ID、元数据、启用状态、版本与校验规则。
2.  **Schema 不重复类型信息**：基础数据类型由现有实体系统负责；Schema
    主要声明必填、枚举、范围、唯一性、引用和业务规则。
3.  **定义与实例分离**：模组中的实体是静态定义；玩家船只、库存、委托进度等属于运行时实例。
4.  **组件组合优先**：船体定义部位，模块定义安装需求与能力；具体装配由船型或装配配置描述。
5.  **模块类型可扩展**：框架提供通用部位类型和模块类别，模组可注册新类型，但不能覆盖已有
    ID 或绕过校验。
6.  **严格发布门禁**：存在阻断级错误时禁止正式发布；警告可保留，但必须清楚呈现。
7.  **避免提前过度建模**：没有玩法和运行时消费者的字段不应仅为"未来可能需要"而加入正式
    Schema。
8.  **单一事实来源**：相同概念只保留一个权威字段，避免展示数据和模拟数据冲突。

------------------------------------------------------------------------

## 2. 实体类型规划

建议目标架构保留以下实体类型。是否立即合并既有类型，应先核对当前代码与运行时职责。

  -------------------------------------------------------------------------------------------------------------------------------------------------------
  目标实体                   当前相关实体                                     处理建议                               职责
  -------------------------- ------------------------------------------------ -------------------------------------- ------------------------------------
  `Item`                     商品 `Product`、造船材料 `Material`              评估统一基础物品定义；市场数据可独立   可持有、消耗、交易或用于制造的物品

  `Hull`                     船体                                             保留                                   船体基础属性与部位布局

  `Module`                   锅炉、货舱、导航模块、安全模块、客舱、船员岗位   合并为统一模块实体                     可安装到船上的功能组件

  `PortTemplate`             港口原型                                         保留                                   港口生成原型与基础能力

  `MapConfig`                地图配置                                         保留                                   世界与地图生成参数

  `StartingScenario`         初始构筑                                         保留并核对语义                         新游戏初始状态、资源与实体配置

  `Quest`                    委托                                             保留                                   委托条件、目标、奖励与生命周期规则

  `VoyageEvent`              航行事件                                         保留                                   航行事件的触发条件、概率与效果

  `ModuleStrategy`（可选）   锅炉策略                                         优先合并进 Module                      可复用的模块行为策略
                                                                              配置；仅在可复用、可独立引用时保留     
  -------------------------------------------------------------------------------------------------------------------------------------------------------

### 2.1 合并规则

-   锅炉、货舱、导航、安全、客舱和船员居住组件统一为 `Module`。
-   合并的是**实体类型和编辑器基础机制**，不是把不同模块的业务属性强行变成完全相同的字段。
-   `Module.module_type`
    决定模块类别；类别专属字段通过相应的规则定义校验。
-   `Product` 与 `Material` 是否合并为
    `Item`，需要核对现有运行时语义。即使统一物品定义，市场价格、供需和交易规则也可以由市场系统独立管理。
-   锅炉策略若只是参数或运行模式，放在 Module 的 `configuration`
    中；只有在需要跨模块复用、独立注册或引用时才抽为 `ModuleStrategy`。

## 3. 通用实体契约

所有标准实体共享以下外层结构：

``` json
{
  "id": "namespace:entity_type/entity_id",
  "name": "Display Name",
  "description": "",
  "tags": [],
  "enabled": true,
  "data": {},
  "information": {}
}
```

### 3.1 通用字段约束

  --------------------------------------------------------------------------------------------------------------
  字段                                约束
  ----------------------------------- --------------------------------------------------------------------------
  `id`                                必填、全局唯一、使用命名空间格式；实体类型路径必须与实体类型一致

  `name`                              必填、非空

  `description`                       可选，缺省时由统一机制处理为空字符串

  `tags`                              可选；同一实体内不得重复

  `enabled`                           必填；禁用实体不得用于新装配、生成或新建运行时对象

  `data`                              必填；保存参与游戏逻辑的权威数据

  `information`                       可选；保存展示、设计参考和非权威资料

  Schema 版本                         由统一内容格式版本机制管理，不要求每个实体重复声明，除非现有架构另有约定
  --------------------------------------------------------------------------------------------------------------

### 3.2 ID 规则

建议格式：

``` text
<namespace>:<entity_type>/<entity_id>
```

示例：

``` text
core:hull/coastal_small
core:module/basic_boiler
core:item/timber
core:port_template/river_port
core:map_config/default_world
core:quest/deliver_timber
core:voyage_event/storm
```

规则：

-   命名空间和 ID
    使用小写字母、数字、下划线、短横线；路径可按现有规范支持 `/`。
-   不允许空格、大小写混用或隐式规范化后冲突。
-   同一注册表内 ID 不得重复。
-   不同模组可以拥有不同命名空间下的同名实体。
-   不允许模组覆盖另一个模组的
    ID；若未来需要覆盖，必须使用显式、可审计的 Patch/Override 机制。
-   引用应使用完整 ID，不使用名称、显示文本或数组位置作为引用。

### 3.3 Schema 约束描述格式

Schema 不重复声明基础
`type`。约束描述只使用项目实际支持的规则关键字，例如：

-   `required`
-   `enum`
-   `min` / `max` / `exclusive_min`
-   `min_length` / `max_length`
-   `min_items` / `max_items`
-   `unique` / `unique_by`
-   `reference`
-   `rules`

这些关键字是建议的语义词汇。正式关键字和序列化形式必须与 SN 当前的
Schema 引擎对齐，不得直接假设现有实现支持所有名称。

未知标准字段应报错。若允许模组扩展字段，应放入明确的 `extensions` 或
`custom_data` 命名空间，并由对应扩展规则验证。

## 4. Hull：船体组件

### 4.1 职责

`Hull`
是可复用的船体组件，不是完整船型，也不是玩家拥有的船只实例。它定义船体基础能力和可安装部位。

Hull 不负责定义发动机燃料消耗、当前耐久、当前库存或玩家改装状态。

### 4.2 数据示例

``` json
{
  "id": "core:hull/coastal_small",
  "name": "Small Coastal Hull",
  "description": "A small hull for coastal trade.",
  "tags": ["hull", "small", "coast"],
  "enabled": true,
  "data": {
    "tier": 1,
    "size_class": "small",
    "operation_profile": "coast",
    "hull_mass": 12000,
    "max_weight": 8000,
    "max_durability": 100,
    "cargo_slots": 12,
    "cabin_slots": 4,
    "base_speed": 1.0,
    "base_risk": 0.15,
    "purchase_price": 1200,
    "craft_time_hours": 24,
    "materials": [
      {
        "id": "core:item/timber",
        "amount": 30
      }
    ],
    "compartments": [
      {
        "id": "engine_room",
        "name": "Engine Room",
        "compartment_type": "core:engine_room",
        "capacity": 10,
        "allowed_module_types": ["engine", "boiler", "auxiliary"]
      },
      {
        "id": "cargo_hold_a",
        "name": "Cargo Hold",
        "compartment_type": "core:cargo_hold",
        "capacity": 12,
        "allowed_module_types": ["cargo_hold", "storage"]
      }
    ]
  },
  "information": {
    "length_m": 18.0,
    "beam_m": 5.0,
    "draft_m": 1.5,
    "model": "core:models/hull/coastal_small"
  }
}
```

数值仅用于示意，不是平衡数据。

### 4.3 字段约束

  --------------------------------------------------------------------------------------------------
  字段                                约束
  ----------------------------------- --------------------------------------------------------------
  `data.tier`                         必填，最小值为 1

  `data.size_class`                   必填，`small` / `medium` / `large`

  `data.operation_profile`            必填，`coast` / `ocean`

  `data.hull_mass`                    必填，正数；单位需由项目统一

  `data.max_weight`                   必填，正数；定义为最大有效载荷，不含船体自身质量

  `data.max_durability`               必填，正数

  `data.cargo_slots`                  必填，非负整数

  `data.cabin_slots`                  必填，非负整数

  `data.base_speed`                   必填，正数；需明确是速度值还是速度系数

  `data.base_risk`                    必填，范围 0--1，定义为船体基础风险值或修正值，二者必须择一

  `data.purchase_price`               裸船体组件的价格，非负

  `data.craft_time_hours`             裸船体制造工时，非负

  `data.materials`                    材料清单；每项引用有效 Item，数量为正整数

  `data.compartments`                 必填数组；每个部位的 ID 在该 Hull 内唯一

  `information.length_m`              可选，正数；展示/设计资料，除非被明确指定为权威模拟值

  `information.beam_m`                可选，正数

  `information.draft_m`               可选，正数；若参与港口准入，权威值应放入游戏数据而不是只放在
                                      `information`

  `information.model`                 可选资源引用；资源必须可解析
  --------------------------------------------------------------------------------------------------

### 4.4 Hull 约束

-   `compartments[].id` 在同一 Hull 内唯一。
-   `compartment_type` 必须引用已注册的部位类型。
-   `capacity` 必须大于 0。
-   `allowed_module_types` 中的每一项必须是已注册的模块类别。
-   `allowed_module_types`
    为空表示该部位不允许安装模块，不允许将空列表解释为"允许全部"。
-   多个部位可以拥有相同 `compartment_type`，但必须拥有不同的局部 ID。
-   `module_slots` 不再作为独立字段；模块容量由各部位容量表达。
-   `cargo_slots`
    表示船体基础货物容量；如果货舱模块也增加容量，必须定义基础容量与模块容量如何相加，避免重复计算。
-   `max_weight`、`hull_mass` 和模块容量属于不同概念，不能相互替代。
-   Hull 的定义数据不得存储玩家船只的当前耐久、已安装模块实例或库存。

## 5. Compartment：部位配置与部位类型注册

Compartment 不是独立的通用内容实体，而是 Hull
中的一个部位配置。独立注册的是 `compartment_type`。

### 5.1 部位配置结构

``` json
{
  "id": "engine_room",
  "name": "Engine Room",
  "compartment_type": "core:engine_room",
  "capacity": 10,
  "allowed_module_types": ["engine", "boiler", "auxiliary"]
}
```

### 5.2 字段约束

  ------------------------------------------------------------------------------------
  字段                                约束
  ----------------------------------- ------------------------------------------------
  `id`                                必填；在当前 Hull 内唯一；仅作为该 Hull
                                      内的局部标识

  `name`                              必填、非空

  `compartment_type`                  必填，引用已注册部位类型

  `capacity`                          必填，正数；抽象容量单位，不代表质量或真实体积

  `allowed_module_types`              必填列表；元素不得重复，均须为已注册模块类别
  ------------------------------------------------------------------------------------

### 5.3 部位类型注册约束

部位类型注册项建议只包含类型身份和通用语义，例如：

``` json
{
  "id": "core:engine_room",
  "name": "Engine Room",
  "description": "A compartment intended for propulsion machinery."
}
```

-   框架提供基础类型，如
    `core:engine_room`、`core:cargo_hold`、`core:deck`、`core:living_quarters`、`core:utility_space`。
-   模组可以注册新类型，例如 `steampunk:boiler_room`。
-   类型 ID 全局唯一，不得覆盖已有类型。
-   新类型必须有明确语义；如果只是分类标签，不应新建部位类型。
-   未注册类型必须报错，不允许静默回退为通用类型。
-   部位类型是轻量注册定义，不应继承完整 Hull/Module
    的价格、制造、耐久等字段。

## 6. Module：统一船舶模块

### 6.1 职责

`Module`
统一承载原有的锅炉、货舱、导航模块、安全模块、客舱和船员居住组件。

合并实体类型并不意味着所有模块使用完全相同的业务字段。模块的共同部分由统一结构定义；不同
`module_type` 的专用能力由对应的类型规则约束。

### 6.2 数据示例

``` json
{
  "id": "core:module/basic_boiler",
  "name": "Basic Boiler",
  "description": "A basic steam boiler.",
  "tags": ["module", "boiler", "steam"],
  "enabled": true,
  "data": {
    "module_type": "boiler",
    "installation": {
      "allowed_compartment_types": ["core:engine_room"],
      "capacity_cost": 4,
      "max_instances_per_compartment": 1,
      "max_instances_per_ship": 1
    },
    "capabilities": {
      "steam_output": 100
    },
    "configuration": {
      "default_strategy": "balanced"
    },
    "purchase_price": 500,
    "craft_time_hours": 8,
    "materials": [
      {
        "id": "core:item/iron_ingot",
        "amount": 10
      }
    ]
  },
  "information": {
    "model": "core:models/modules/basic_boiler"
  }
}
```

数值仅用于示意。

### 6.3 通用字段约束

  ------------------------------------------------------------------------------------------
  字段                                                约束
  --------------------------------------------------- --------------------------------------
  `data.module_type`                                  必填，引用已注册的模块类别

  `data.installation.allowed_compartment_types`       必填列表；必须引用已注册的部位类型

  `data.installation.capacity_cost`                   必填，正数

  `data.installation.max_instances_per_compartment`   可选，正整数

  `data.installation.max_instances_per_ship`          可选，正整数

  `data.capabilities`                                 模块能力数据；由 `module_type`
                                                      对应的专用规则验证

  `data.configuration`                                模块配置；由对应类型规则验证

  `data.purchase_price`                               可选，非负；如果模块可单独购买才需要

  `data.craft_time_hours`                             可选，非负；如果模块可单独制造才需要

  `data.materials`                                    可选制造材料清单；引用有效 Item

  `information.model`                                 可选资源引用，必须可解析
  ------------------------------------------------------------------------------------------

### 6.4 Module 约束

-   `module_type` 必须是已注册模块类别。
-   `allowed_compartment_types` 必须引用已注册部位类型。
-   `capacity_cost` 必须大于 0。
-   数量限制未声明时，表示不额外设置该项数量上限，但仍受容量与兼容性限制。
-   若 Module 声明额外安装前置条件，条件必须使用框架支持的规则格式。
-   `module_type` 与 `allowed_compartment_types`
    必须同时满足；两者冲突时判定为不兼容。
-   Module 的定义不保存当前安装在哪艘船、当前耐久、剩余燃料或运行状态。
-   不能因模块名称相似就推断其类型或兼容性；必须读取明确字段。

### 6.5 模块类别与专用能力

框架可以内置常见类别，例如：

-   `boiler`
-   `engine`
-   `cargo_hold`
-   `navigation`
-   `safety`
-   `passenger_cabin`
-   `crew_quarters`
-   `auxiliary`
-   `storage`

这些类别不是不可扩展的固定枚举。模组可以注册新类别，但必须提供对应的字段规则、能力语义和运行时支持。只注册一个字符串并不意味着游戏自动知道如何执行该模块。

示例：

  ----------------------------------------------------------------------------------------------
  模块类别                专用能力示例                  约束方向
  ----------------------- ----------------------------- ----------------------------------------
  `boiler`                `steam_output`                输出值大于 0

  `engine`                `power_output`、`fuel_type`   功率合法，燃料引用有效

  `cargo_hold`            `cargo_slots` 或              容量非负；必须统一槽位制或容量制的语义
                          `cargo_capacity`              

  `navigation`            `navigation_bonus`            数值范围由导航系统定义

  `safety`                `risk_reduction`              不得超出风险系统允许的范围

  `passenger_cabin`       `passenger_capacity`          非负整数

  `crew_quarters`         `crew_capacity`               非负整数
  ----------------------------------------------------------------------------------------------

## 7. Module 装配与组合校验

装配配置负责记录某艘船型使用哪个 Hull，以及具体模块安装在哪个部位。Hull
和 Module 本身只提供可复用定义。

### 7.1 装配示例

``` json
{
  "hull": "core:hull/coastal_small",
  "modules": [
    {
      "module": "core:module/basic_boiler",
      "compartment": "engine_room"
    }
  ]
}
```

如果当前项目已有 `ShipDesign`
或等价的船型/装配实体，应将装配规则放到该实体中；不要为了本文示例再创建重复的实体类型。

### 7.2 组合规则

  ------------------------------------------------------------------------------------------------------
  规则 ID                 规则                                                   错误级别
  ----------------------- ------------------------------------------------------ -----------------------
  `HCM-001`               Hull 内部位 ID 必须唯一                                Error

  `HCM-002`               Hull 引用的部位类型必须已注册                          Error

  `HCM-003`               Module 引用的部位类型必须已注册                        Error

  `HCM-004`               Module 容量占用必须大于 0                              Error

  `HCM-005`               模块类别必须被目标部位允许                             Error

  `HCM-006`               Module 的允许部位类型必须与目标部位类型兼容            Error

  `HCM-007`               同一部位所有已安装模块的容量占用总和不得超过部位容量   Error

  `HCM-008`               不得超过模块的单部位数量上限                           Error

  `HCM-009`               不得超过模块的整船数量上限                             Error

  `HCM-010`               模块的安装前置条件必须全部满足                         Error

  `HCM-011`               所有引用的 Hull、Module 和类型都必须存在且可用         Error
  ------------------------------------------------------------------------------------------------------

### 7.3 容量计算

部位容量使用抽象容量单位：

``` text
used_capacity(compartment)
    = sum(module.installation.capacity_cost)

valid
    = used_capacity(compartment) <= compartment.capacity
```

例如，容量为 10 的动力舱可以安装容量消耗分别为 4、4、2
的三个模块；再安装容量消耗为 1 的模块即超限。

此版本只使用抽象容量，不引入质量限制或二维格子布局。若未来引入质量限制，应作为独立约束新增，而不是改变
`capacity` 的含义。

### 7.4 空部位与缺少设备

-   Hull 定义了动力舱但没有配置任何发动机，不应单独导致 Hull 发布失败。
-   若 ShipDesign
    声明必须具备主推进系统，则该装配必须包含符合要求的动力模块。
-   空部位允许存在，除非船型规则明确要求安装某类模块。
-   不能默认所有船型都必须有锅炉或发动机；纯帆船等配置应当可以合法存在。

## 8. Item：物品与制造材料

### 8.1 职责

建议以 `Item`
统一物品基础定义。商品与材料的区别优先由用途、标签、配方引用和市场配置表达，而不是维护重复的基础物品实体。

### 8.2 示例

``` json
{
  "id": "core:item/timber",
  "name": "Timber",
  "description": "Processed timber for ship construction.",
  "tags": ["material", "trade_good"],
  "enabled": true,
  "data": {
    "stack_limit": 100,
    "unit_weight": 1,
    "unit_volume": 1
  },
  "information": {
    "icon": "core:icons/timber"
  }
}
```

数值仅为示意；若当前经济系统不使用重量或体积，可以不启用对应字段。

### 8.3 约束

-   物品 ID 全局唯一。
-   制造材料和委托目标必须引用有效 Item。
-   数量必须满足对应规则，消耗或配方数量通常要求大于 0。
-   `stack_limit` 若存在，必须为正整数。
-   `unit_weight`、`unit_volume` 若存在，必须非负。
-   市场价格、港口供需和价格波动应由市场系统或市场配置负责，避免同一个物品在多个实体中维护互相冲突的价格。
-   若暂时保留旧的 `Product` 与 `Material`，应定义迁移映射，明确何时使用
    Item ID，避免同时维护两套基础物品数据。

------------------------------------------------------------------------

## 9. PortTemplate：港口原型

### 9.1 职责

定义可生成港口的基础模板，不代表世界中的某一个实际港口实例。

### 9.2 建议数据结构

``` json
{
  "id": "core:port_template/river_port",
  "name": "River Port",
  "description": "A small port serving shallow waterways.",
  "tags": ["river", "coastal_trade"],
  "enabled": true,
  "data": {
    "port_size": "small",
    "max_draft": 2.0,
    "facilities": ["market", "repair"],
    "trade_profile": "regional"
  },
  "information": {}
}
```

### 9.3 约束

-   港口规模必须属于已定义的合法等级。
-   `max_draft` 若用于船舶准入判定，必须为正数并采用统一单位。
-   `facilities` 中的设施 ID 必须已注册。
-   `trade_profile` 必须引用已注册的贸易配置，或使用框架声明的合法枚举。
-   港口原型引用的商品或交易配置必须有效。
-   港口模板不保存实际港口的动态库存、当前价格、当前设施损坏等运行时状态。

------------------------------------------------------------------------

## 10. MapConfig：地图配置

### 10.1 职责

定义世界生成的规则与参数，不保存已生成世界的动态状态。

### 10.2 建议数据结构

``` json
{
  "id": "core:map_config/default_world",
  "name": "Default World",
  "description": "Default procedural world configuration.",
  "tags": ["default"],
  "enabled": true,
  "data": {
    "map_size": "medium",
    "seed_policy": "random",
    "port_templates": [
      {
        "id": "core:port_template/river_port",
        "weight": 3
      }
    ]
  },
  "information": {}
}
```

### 10.3 约束

-   地图尺寸、生成模式和种子策略必须是合法值。
-   所有港口模板引用必须存在且启用。
-   生成权重必须为非负数；如果生成列表需要抽样，权重总和必须大于 0。
-   参数上下限应由地图生成器声明，不应由每个模组任意设定不一致的范围。
-   地图配置不能直接引用不存在的实体或通过字符串拼接绕过引用校验。
-   随机生成结果属于运行时产物，不回写到 MapConfig 的原始定义中。

## 11. StartingScenario：初始场景

首先需确认现有"初始构筑"是否确实表示新游戏的初始世界和玩家状态。如果它表示地图建筑布局，则应改为对应的世界构筑实体，不应与玩家初始配置混为一谈。

### 11.1 建议数据结构

``` json
{
  "id": "core:starting_scenario/default",
  "name": "Default Start",
  "description": "A standard new-game starting scenario.",
  "tags": ["default"],
  "enabled": true,
  "data": {
    "map_config": "core:map_config/default_world",
    "starting_items": [
      {
        "item": "core:item/timber",
        "amount": 10
      }
    ],
    "starting_hull": "core:hull/coastal_small"
  },
  "information": {}
}
```

### 11.2 约束

-   `map_config` 必须引用有效且启用的地图配置。
-   初始物品必须引用有效 Item，数量必须符合库存规则。
-   `starting_hull` 必须引用有效 Hull。
-   如果初始场景指定模块或完整船型，相关引用和装配必须通过组合校验。
-   初始资源不得为非法负数。
-   场景定义不应直接保存玩家后续游戏进度。

## 12. Quest：委托

### 12.1 职责

定义委托的可接受条件、目标、奖励和生命周期规则。玩家是否已接受、当前进度和完成状态属于运行时实例。

### 12.2 建议数据结构

``` json
{
  "id": "core:quest/deliver_timber",
  "name": "Deliver Timber",
  "description": "Deliver timber to the target port.",
  "tags": ["delivery"],
  "enabled": true,
  "data": {
    "objectives": [
      {
        "type": "deliver_item",
        "item": "core:item/timber",
        "amount": 10,
        "target_port": "core:port_template/river_port"
      }
    ],
    "rewards": [
      {
        "type": "currency",
        "amount": 100
      }
    ],
    "conditions": [],
    "repeatable": false
  },
  "information": {}
}
```

### 12.3 约束

-   委托目标类型必须已注册。
-   目标所引用的 Item、港口或其他实体必须存在。
-   目标数量必须满足对应规则，通常大于 0。
-   奖励类型必须已注册，奖励参数必须符合该类型规则。
-   `conditions` 必须使用框架支持的条件表达式。
-   不允许引用无法解析的条件、目标或效果。
-   若支持前置委托，引用必须存在；依赖关系不得形成不允许的循环。
-   重复委托、过期和失败规则必须有明确语义，不能依赖未声明的默认行为。
-   委托进度和完成状态属于运行时数据，不写回静态 Quest 定义。

------------------------------------------------------------------------

## 13. VoyageEvent：航行事件

### 13.1 职责

定义在航行过程中可能触发的事件，包括触发条件、发生概率、效果和重复规则。

### 13.2 建议数据结构

``` json
{
  "id": "core:voyage_event/storm",
  "name": "Storm",
  "description": "A storm affects the voyage.",
  "tags": ["weather", "risk"],
  "enabled": true,
  "data": {
    "trigger": {
      "type": "voyage_started"
    },
    "weight": 10,
    "conditions": [],
    "effects": [
      {
        "type": "increase_voyage_risk",
        "amount": 0.1
      }
    ],
    "cooldown_hours": 24,
    "repeatable": true
  },
  "information": {}
}
```

示例中的触发类型、效果名称和数值仅用于说明结构；正式值必须与实际事件系统支持的规则一致。

### 13.3 约束

-   触发器类型必须已注册。
-   发生权重必须非负；参与同一抽样池的有效权重总和必须大于 0。
-   条件表达式必须可解析。
-   效果类型必须已注册，效果参数必须符合对应规则。
-   冷却时间若存在，必须非负。
-   事件效果引用的 Item、Quest、港口或其他实体必须有效。
-   不允许通过未注册脚本、任意代码或未知效果名绕过安全与校验机制。
-   事件是否可以重复触发必须明确声明或采用统一默认值。
-   事件触发记录、冷却状态和已执行效果属于运行时状态，不写回静态定义。

------------------------------------------------------------------------

## 14. ModuleStrategy：可选的策略实体

锅炉策略不应仅因为它在编辑器里有单独菜单，就必须保留为独立实体。

### 14.1 合并进 Module 的情况

如果策略只是锅炉的局部参数，例如：

-   节能模式
-   平衡模式
-   高输出模式

且只被该锅炉类型使用，建议直接放入：

``` json
{
  "configuration": {
    "default_strategy": "balanced",
    "available_strategies": ["economy", "balanced", "high_output"]
  }
}
```

这些字符串必须由锅炉类型的规则定义，而不能任意输入。

### 14.2 保留独立策略实体的情况

只有在策略需要跨多个模块复用、由其他实体引用、独立启用/禁用或由模组独立扩展时，才建议保留
`ModuleStrategy`。

如果保留，应具有：

-   唯一 ID
-   策略类型
-   参数配置
-   适用模块类别
-   对应的参数校验规则

策略实体必须由运行时明确支持；仅仅创建一份 JSON 定义并不会自动产生行为。

------------------------------------------------------------------------

## 15. 通用条件与效果规则

Quest、VoyageEvent 和部分 Module
配置可能共享条件或效果。建议将它们设计为统一的声明式规则系统，而不是让各实体重复发明条件语言。

### 15.1 条件规则

候选条件类型：

-   `has_item`
-   `arrived_at_port`
-   `voyage_started`
-   `cargo_value_at_least`
-   `quest_completed`
-   `module_installed`

每种条件必须定义必填参数、引用要求、合法比较符和运行时解释方式。

### 15.2 效果规则

候选效果类型：

-   `grant_item`
-   `grant_currency`
-   `remove_item`
-   `update_quest_progress`
-   `increase_voyage_risk`
-   `apply_module_modifier`

每种效果必须定义参数 Schema、合法目标、数值边界和执行失败策略。

### 15.3 规则约束

-   未注册条件或效果类型必须报错。
-   所有实体引用必须解析成功。
-   不允许把任意脚本字符串当作有效条件或效果。
-   条件求值和效果执行必须由框架负责。
-   规则配置通过静态校验，不代表运行时效果一定成功；运行时仍需检查状态前置条件。
-   若规则系统支持嵌套，应限制递归深度并检测非法循环。

------------------------------------------------------------------------

## 16. 模组注册、依赖与引用规则

### 16.1 注册顺序

建议加载和发布校验遵循以下逻辑顺序：

1.  读取模组元数据与依赖声明。
2.  检查命名空间、模组 ID 和依赖版本。
3.  建立实体索引并检测重复 ID。
4.  注册部位类型、模块类别、条件类型和效果类型。
5.  校验各实体自身的字段与局部约束。
6.  校验跨实体引用。
7.  校验 Hull / Module / ShipDesign 的组合关系。
8.  校验 MapConfig、StartingScenario、Quest、VoyageEvent 的引用与规则。
9.  生成统一的错误与警告报告。
10. 无阻断级错误时才允许正式发布。

如果当前架构要求先构建临时注册表再冻结，应在临时注册表上完成校验；只有通过后才冻结并生成可发布产物。

### 16.2 引用约束

-   引用使用完整实体 ID。
-   不允许用实体显示名称代替 ID。
-   目标实体必须存在且启用，除非引用规则明确允许禁用实体作为编辑期占位。
-   跨模组引用必须声明有效依赖，或遵循框架定义的公共依赖机制。
-   不允许覆盖其他模组注册的 ID。
-   Patch/Override 必须显式声明目标和预期版本，且经过单独的冲突检查。
-   被其他启用实体引用的实体被禁用时，应报告依赖错误，不能静默跳过。

### 16.3 循环依赖

-   模组依赖关系不允许存在框架不支持的循环。
-   规则表达式、委托前置条件和实体继承关系若存在，应按各自规则检查循环。
-   普通的双向引用不一定构成依赖循环；是否允许应由具体引用类型定义，而不是一概禁止所有循环引用。

------------------------------------------------------------------------

## 17. 错误等级与正式发布门禁

建议只保留三种结果级别：

  级别        含义                                     是否阻止发布
  ----------- ---------------------------------------- --------------
  `error`     数据无效、引用缺失、结构或组合规则冲突   是
  `warning`   可运行但存在设计风险、冗余或不推荐配置   否
  `info`      提示、迁移信息或优化建议                 否

正式发布门禁：

-   只要存在一个 `error`，发布失败。
-   `warning` 不阻止发布，但应在编辑器和发布报告中可见。
-   不允许将未知字段、未知引用或未知规则静默降级为 `warning`。
-   允许用户明确禁用某个实体，但禁用实体不得被启用的正式内容引用。
-   编辑期草稿可以暂时存在错误，但不能打包为正式发布产物。

### 17.1 错误报告格式

``` json
{
  "code": "HCM-007",
  "severity": "error",
  "entity_id": "core:hull/coastal_small",
  "path": "data.compartments[0].capacity",
  "message": "Installed modules exceed compartment capacity.",
  "related_entities": [
    "core:module/basic_boiler"
  ]
}
```

字段含义：

-   `code`：稳定的错误代码，用于测试和自动化处理。
-   `severity`：`error`、`warning` 或 `info`。
-   `entity_id`：当前问题所属实体。
-   `path`：出错字段路径。
-   `message`：面向开发者的说明。
-   `related_entities`：可选，列出相关实体。

错误代码可以按领域划分，例如
`ENT-*`、`REF-*`、`HCM-*`、`MAP-*`、`QST-*`、`EVT-*`。

------------------------------------------------------------------------

## 18. SNModMaker 编辑器约束

建议采用"通用实体编辑器 + 少量专用编辑器"的结构。

### 18.1 通用编辑器负责

-   通用元数据编辑
-   Schema 驱动的字段表单
-   枚举和数值约束
-   实体引用选择器
-   ID 唯一性检查
-   未知字段检测
-   错误路径定位
-   草稿保存与正式发布校验

### 18.2 专用编辑器负责

  编辑器                     专用功能
  -------------------------- --------------------------------
  Hull / Module 装配编辑器   显示部位、容量占用和模块兼容性
  MapConfig 编辑器           地图参数与生成预览
  StartingScenario 编辑器    初始资源与场景配置
  Quest 编辑器               委托目标、前置条件和奖励流程
  VoyageEvent 编辑器         触发条件、概率和效果配置

专用编辑器可以提供更好的交互，但不能使用独立规则绕过统一校验器。

------------------------------------------------------------------------

## 19. 迁移策略

不要一次性重写所有实体和编辑器。建议分阶段迁移。

### Phase 1：盘点并冻结当前契约

-   导出当前所有实体类型、字段和引用关系。
-   查清现有 Schema 引擎支持的规则关键字。
-   查清运行时哪些字段被实际读取。
-   为现有内容建立基线测试。
-   确认 `StartingScenario`、`Product`、`Material` 和 `BoilerStrategy`
    的真实业务语义。

### Phase 2：统一基础校验器

-   建立通用实体契约。
-   统一 ID、唯一性、引用和错误报告。
-   建立注册表与正式发布门禁。
-   不改变游戏运行时行为。

### Phase 3：合并船舶模块实体

-   将锅炉、货舱、导航、安全、客舱和船员岗位迁移为 Module。
-   为每个模块类别建立专用规则。
-   将锅炉策略按实际复用情况合并或独立化。
-   提供旧实体到新实体的迁移映射。

### Phase 4：建立跨实体校验

-   实现 Hull / Compartment / Module 的组合校验。
-   迁移制造材料和物品引用。
-   校验港口与地图生成引用。
-   校验委托与航行事件条件、效果。

### Phase 5：统一编辑器体验

-   将通用字段编辑迁移到 Schema 驱动的表单。
-   为地图、装配、委托等保留专用可视化。
-   确保 UI 校验与发布校验共用相同的规则实现。

### Phase 6：清理旧格式

-   旧格式迁移成功后，停止生成旧实体格式。
-   对旧实体提供明确的弃用提示。
-   删除旧格式支持前，确认已有模组和测试全部迁移。
-   保留必要的格式版本迁移工具。

------------------------------------------------------------------------

## 20. 验收标准

重构完成后，至少应满足以下条件：

-   [ ] 所有实体都遵守统一的基础契约。
-   [ ] 所有实体 ID 唯一且格式合法。
-   [ ] 所有实体引用均可解析。
-   [ ] 未知字段、未知类型和未知规则会产生明确错误。
-   [ ] 第三方模组能够注册新的部位类型和模块类别，且不能覆盖已有注册项。
-   [ ] Hull 可以定义多个同类型部位。
-   [ ] Module 可以安装到兼容部位，一个部位可以安装多个 Module。
-   [ ] 部位容量计算准确，超限装配会阻止正式发布。
-   [ ] 模块数量限制与安装前置条件能够被正确检查。
-   [ ]
    商品、材料、港口、地图、初始场景、委托和航行事件的引用规则有对应测试。
-   [ ] 未通过校验的内容不能生成正式发布产物。
-   [ ] 错误报告包含稳定错误码、实体 ID 和字段路径。
-   [ ] 编辑器表单与正式发布使用同一套校验规则。
-   [ ] 现有 Core 内容迁移后，原有可用玩法没有非预期回归。

## 21. 尚待现有代码确认的事项

以下事项不应仅根据设计文档直接定案：

1.  当前 Schema 引擎的实际格式、支持的关键字与默认值处理方式。
2.  当前注册表、Patch 和冻结流程如何处理跨模组引用。
3.  `Product` 与 `Material` 是否已经拥有不同的运行时行为。
4.  "初始构筑"究竟是世界建筑布局还是玩家初始配置。
5.  锅炉策略是否被其他实体或运行时系统独立引用。
6.  现有船舶系统是否已经有 `ShipDesign`、装配配置或等价结构。
7.  `base_speed`、`base_risk`、`max_weight` 和 `cargo_slots`
    在当前计算逻辑中的真实语义。
8.  第三方模组注册新的模块类别时，框架是否具备相应的能力执行机制。

在这些事项得到核对前，本文应作为目标架构和实施依据，而不是直接覆盖现有
Schema 的最终实现文件。

## 附录 B：核心架构结论

SN 的模组系统应由以下部分组成：

1.  **实体定义层**：保存静态内容数据。
2.  **Schema 层**：声明字段、枚举、范围和局部约束。
3.  **注册表层**：管理命名空间、实体唯一性、类型注册与引用。
4.  **语义校验层**：检查跨实体关系、组合容量和规则可解析性。
5.  **运行时层**：执行航行、经济、模块能力、委托和事件逻辑。
6.  **编辑器层**：提供通用表单与专用可视化，但不重复实现业务规则。
7.  **发布门禁层**：保证所有正式产物通过统一校验。

最终目标不是让每种实体拥有越来越复杂的独立 Schema，而是让 SN
通过一套稳定、可扩展的实体契约和校验体系，安全地加载 Core
与第三方模组内容。
