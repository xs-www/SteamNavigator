# 战斗系统架构评审：外部草案 SN-ARCH-COMBAT-001

> 来源：外部草案 `Combat_System_Architecture.md`（Document ID `SN-ARCH-COMBAT-001`，Architecture baseline / proposed，v0.1.0）。
> 状态：评审结论；只记录“采纳什么、改写什么、暂缓什么”，不代表战斗系统已进入实现。
> 相关：[路线图](FULL_GAME_ROADMAP.md#阶段-2舰队与战斗)、[实体契约 v2](ENTITY_CONTRACT_V2.md)、[持久战役架构](PERSISTENT_CAMPAIGN_ARCHITECTURE.md)。

## 1. 总评

草案的**分层与约束**对项目有用，**时间模型与规模假设**与当前路线图冲突，**依赖的实体模型**尚未落地。结论：

- 采纳为**契约词汇与验收清单**：三表示、遭遇生命周期、终态不可变、结算幂等、单船完整性、命令即意图、能力注册表、伤害分级递进、遭遇级随机流、严格校验。
- 不采纳其**第一步做实时战术**的排期：本项目路线图明确“先自动结算 + 少量选择，再评估战术层”；且当前航行是事件驱动的时间推进，没有战斗场景/物理层。
- 不能立即落地其**持久伤害与模块失效**：当前 `ship` 只存模块 ID，没有模块实例 condition；需要先完成 Module 实例化（阶段 2 前置）。
- 草案假设的 Hull / Compartment / 统一 Module 模型来自 `Steam_Navigator_Mod_Entity_Constraints_Spec.md`（Draft 0.1）；本项目已决定 Module/Item 合并与 Compartment 模型**推迟**，因此战斗数据 Schema 不提前按该模型编写。

## 2. 与现有契约的对照

| 草案主张 | 项目现状 | 结论 |
| --- | --- | --- |
| 定义 / 持久实例 / 运行时三表示 | `ENTITY_CONTRACT_V2` §8 定义 / 生成参数 / 运行态三分类 | 同构，合并表述即可；运行态只存 ID 与数值 |
| 遭遇状态机 + 终态不可变 + 结算幂等 | 命令事务（克隆执行、成功才提交）已提供幂等基础 | 采纳；终局结算走单个命令 |
| 单船即完整参与者，舰队是扩展 | 路线图阶段 2 才做多船；MVP 单船 | 采纳，先把单船闭环做完整 |
| 命令表达意图，AI/系统执行 | 项目已是 Command/Query + 操作码；UI 不直接改状态 | 采纳；玩家指令映射为 `combat.*` 命令 |
| 能力提供者注册表替代枚举 | 项目用内容类型 + `EffectOpRegistry` 操作码白名单 | 采纳模式；禁止内容数据执行代码 |
| 战斗复用导航运动模型 | 当前航行是数值结算，无实体运动 | 保留为约束；自动结算阶段用同一套航速/补给参数 |
| 伤害分级：整船 → 部位 → 高级 | 当前只有船级 `durability` | 采纳递进；第一阶段只做整船 + 简单模块规则 |
| 遭遇级随机源 | `RngService` 命名流（架构文档已预留 `combat:*`） | 采纳；新增流不得扰动旧流 |
| 未知能力/引用发布期报错 | `CrossReferenceValidator` + 发布门禁 error/warning 分级 | 完全一致，直接沿用 |
| 实时连续模拟、无回合 | 进度是 `game_time` 推进 + 事件驱动 | **冲突**：先自动结算，战术层后置 |
| 部位/舱室伤害、复杂穿甲、弹道 | 无部位模型 | 暂缓，等 Compartment 专项 |

## 3. 建议立即采纳（只写契约，不写代码）

1. **三表示纪律**：战斗定义（武器/敌人原型/遭遇表/掉落表）只进注册表；船只与模块的耐久、失效、安装引用进战役存档；目标、指令、冷却只活在运行时。
2. **遭遇生命周期**：`INITIALIZING → ENGAGING → RETREATING → RESOLVING → 终态 → FINALIZED`；初始化失败走 `ABORTED`，不得扣费或造成伤害；终态不可再结算。
3. **结算幂等**：一次遭遇只能产生一次结算结果；奖励/消耗/伤害在单个命令事务内提交，重复调用返回已结算。
4. **单船完整**：任何战斗功能不得以“必须先有舰队”为前提；舰队是乘数，不是依赖。
5. **命令即意图**：首批指令集 `ATTACK_TARGET` / `APPROACH` / `MAINTAIN_RANGE` / `RETREAT`，映射到 `combat.order` 命令并持久化在运行态；无效目标必须确定性处理（标记失效 + 回退默认行为）。
6. **伤害分级**：第一版只做整船耐久 + 显式指定的模块失效；部位伤害、穿甲、弹道留给后续。
7. **严格校验**：未知武器/敌人/遭遇表/能力声明在发布门禁报 `error`；运行时不得静默造默认值。
8. **测试矩阵**：草案 §13 的 12 条直接作为阶段 2 的测试清单（初始化/非法参与者、状态迁移、指令持久、运动上限、射程/冷却/资源、命中与伤害、模块失效、持久化、撤退不回血、恰好一次结算、未知能力拒绝、数据驱动新模块）。

## 4. 需要改写后再采纳

- **“实时连续模拟”改为“自动结算优先，战术层可选”**：自动结算阶段仍用连续时间，但只在结算点计算；若后续做实时战术，草案 §8/§9 作为该层基线，且必须复用导航参数而不是另建物理。
- **“2v2”与“单船”**：路线图验收要求 2v2 自动结算；草案要求单船可独立完成。两者可调和：单船闭环 → 2v2 自动结算 → 舰队编组 → （可选）实时战术。
- **“能力提供者”落成项目术语**：不新增独立枚举，优先复用内容类型的 `capability` 字段 + 操作码注册表；确需新能力时按 Mod API 版本走注册。

## 5. 暂缓 / 不作为当前范围

- 实时战斗场景、战斗 UI、AI 行为树、弹道与命中特效。
- Compartment（部位）模型与部位伤害；Hull/Compartment/Module 统一迁移。
- 多船编队战斗、登舰、俘虏。
- 草案未覆盖、但项目必须先补的接入点：遭遇如何从区域/地点/航线生成、战利品如何进入 `market`/`warehouse`、失败如何接债务/救援（见持久战役架构 §4）。

## 7. 对 `content_types.json` planned 战斗类型的调整建议

暂不改 manifest（仍为 planned、无 Schema），但记录目标字段方向，避免将来按旧草案误建：

- `weapons`：`weapon_kind`（cannon / harpoon / ram / mine…）、`base_damage`、`range`/`firing_arc`、`cooldown`、`ammo`/`coal` 消耗、`module_category` 约束。
- `damage_types`：作为注册表内容类型（`kinetic` / `explosive` / `fire` / `shock`…），被武器与防御引用；不做大型相克矩阵。
- `combat_abilities`：能力/行为参数（接近、保距、撤退），与操作码分离：能力是数据，执行是框架。
- `enemy_archetypes`：船体/模块组合 + AI 档案 + 掉落表引用。
- `encounter_tables` / `loot_tables`：权重表，沿用现有加权抽样与命名随机流约定。
- 不新增 `compartment_types`、`weapon_providers` 等类型，直到 Compartment / 能力注册专项立项。

## 9. 待决策（继承草案 §16，按项目语境改写）

1. 战斗空间：抽象距离/航段，还是 2D 海面场景。
2. 武器模型：抽象命中判定，还是弹道与射界。
3. 侦测模型：遭遇即互相可见，还是传感器/能见度获取。
4. 伤害拓扑：整船优先，还是部位优先。
5. 撤退规则：距离/时间/边界，还是遭遇脚本。
6. 玩家信息 UI：敌方耐久、武器就绪与意图的可见度。
7. 失败语义：失效、被俘、沉没、逃脱，以及是否接入债务/救援。
8. 时间与资源：锅炉、燃料、弹药、热量与功率在战斗中如何结算。
